# Go Best Practices Reference

## 1. 依存と構成

- 標準ライブラリで解決できる要件は外部依存を増やさない。
- package の公開範囲は最小化し、不要な `exported` 識別子を避ける。
- `cmd/` は起動責務だけにして、業務ロジックは `internal/` に置く。

## 2. 命名と可読性

- 変数名は省略しすぎず、役割が分かる名前にする。
- receiver 名は1文字で十分だが、型名との対応を保つ。
- コメントは「なぜ」を補足し、「何をしているか」の重複説明は避ける。

## 3. エラーハンドリング

- `if err != nil` は早期 return でネストを浅く保つ。
- エラーを再送出する時は文脈を付与して `%w` でラップする。
- 入力検証エラーと内部エラーを区別し、API 層で適切なステータスに変換する。

## 4. Context の扱い

- `context.Context` は第1引数で受け取る。
- `context` を struct に保持しない。
- タイムアウトやキャンセルは呼び出し元に責務を置く。

## 5. インターフェース設計

- interface は実装側ではなく利用側に置く。
- 単一責務を守るため、メソッド数は最小限にする。
- テストのためだけの広すぎる interface を作らない。

## 6. 並行処理

- goroutine は起動条件と終了条件を明確にする。
- `context` と `sync.WaitGroup` で終了制御を行う。
- 共有可変データは避け、必要な場合は `mutex` またはチャネルで保護する。

## 7. テスト戦略

- ユースケース層はテーブル駆動テストを基本にする。
- 時刻・乱数・外部I/Oは差し替え可能にして deterministic にする。
- 正常系だけでなく境界値と異常系を必ず追加する。

## 8. ログと観測性

- `slog` などの構造化ログで key/value を揃える。
- 個人情報や秘密情報をログに残さない。
- エラー時は原因追跡に必要な文脈（操作名、ID、入力の要点）を含める。

## 9. レビュー観点

- ビジネスルールがハンドラに漏れていないか。
- ドメイン概念とDBスキーマの都合が混在していないか。
- 変更に対して十分なテストが追加されているか。
- 後方互換性を壊す変更がないか。

## 10. 実行チェック

Go プロジェクトでは、最低限以下を通す。

```bash
make fmt
make vet
make lint
make test
```

統合ターゲットがあればそれを優先する。

```bash
make check
```
