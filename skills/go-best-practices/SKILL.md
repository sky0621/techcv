# Go Best Practices

## 概要

Goの実装方針を、可読性・保守性・テスト容易性・運用性の観点で揃える。
提案時は抽象論ではなく、対象コードに対する具体的な差分と根拠を示す。

## ワークフロー

1. 変更対象のファイルと実行コマンドを確認する。
2. まずコンパイル/テスト/リンター結果を取得し、壊れている箇所を特定する。
3. 設計と実装を点検する。
4. テスト戦略を点検する。
5. 最小変更で効果が高い改善から適用する。
6. 変更後に再度テストとリンターを実行する。
7. 実施した変更と残課題を短く報告する。

## 設計・実装で守ること

- package は責務ごとに分け、循環参照を作らない。
- interface は使う側で定義し、最小メソッドに絞る。
- `context.Context` は第1引数に置き、保持しない。
- エラーは握りつぶさず、`fmt.Errorf("...: %w", err)` で文脈を付ける。
- ログは `slog` などの構造化ログを使い、機密情報を含めない。
- グローバル可変状態を避け、依存は注入する。

## テストで守ること

- 仕様を表す単体テストを優先する。
- 外部依存（時刻/DB/API）は抽象化して差し替え可能にする。
- `t.Parallel()` は共有状態がない場合のみ使う。
- 失敗メッセージには期待値と実値を含める。

## 変更方針

- 破壊的変更より後方互換な改善を優先する。
- 1つのPR/コミットで1つの意図に絞る。
- generated code は手修正しない。
